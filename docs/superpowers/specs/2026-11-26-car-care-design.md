# 내 차 맞춤 정비 추천 서비스 — 설계 문서

- 작성일: 2026-11-26
- 상태: 초안 (승인 대기)
- 서비스 이름(가칭): **마이카노트 (MyCar Note)**
- 기간·인원: 1인 개발, 4주 (+ 사전 검증 3일)

---

## 1. 개요

### 1.1 한 줄 정의
사용자가 자기 차량과 주행 습관을 등록하면, **"내 차는 지금 무엇을 언제 정비해야 하는가"**를 자동으로 계산해 알려주고, 필요한 순간에 근처 정비소·부품 최저가·관련 소식으로 연결해주는 웹 서비스.

### 1.2 왜 만드는가 (의도)
- **포트폴리오용** 프로젝트다. 프론트엔드뿐 아니라 백엔드(DB, 서버 로직, 예약 작업, 외부 API 연동, 배포 자동화)까지 혼자 설계·구현했다는 것을 보여주는 것이 목적이다.
- 가짜(목업) 데이터가 아니라 **실제 데이터를 최대한** 사용한다.
- 리뷰어(면접관·채용 담당자)가 가장 먼저 봐야 할 부분은 **"내 차에 맞춘 정비 시기 추천"과 "알림"**이다. 나머지 기능(지도, 최저가, 뉴스)은 이 핵심 흐름을 보조한다.

### 1.3 핵심 차별점
1. **주행거리 자동 추정** — 사용자가 매번 주행거리를 입력하지 않아도, 일 평균 주행거리로 오늘의 주행거리를 추정한다.
2. **실측 기반 보정** — 정비 기록·계기판 입력이 쌓이면 실제 주행 패턴을 계산해 추정치를 스스로 교정하도록 제안한다.
3. **차량별 규칙** — 연료 타입(가솔린/디젤/LPG/하이브리드/전기)에 따라 정비 항목과 주기가 달라진다. (예: 전기차는 엔진오일 없음)
4. **기능 간 연결** — 알림 → 정비 항목 상세 → "근처 정비소 지도" / "이 부품 최저가" 로 이어지는 하나의 흐름.

## 2. 목표 · 비목표 · 안티골

### 2.1 목표 (Goals)
- G1. 차량 등록 후 **3분 안에** 사용자가 자기 차의 정비 현황 대시보드를 본다.
- G2. 정비 시기가 다가오면 사용자가 사이트를 열지 않아도 **Web Push 알림**을 받는다.
- G3. 주행거리 추정 → 정비 시기 계산 → 알림 발송까지의 로직이 **서버에서 직접 작성한 코드**로 존재하고, 단위 테스트로 검증된다.
- G4. 지도·최저가·뉴스 데이터는 **실제 외부 API**(카카오, 네이버)에서 가져온다.
- G5. GitHub Actions로 CI(검사·테스트·빌드)와 CD(Cloudflare 배포)가 자동화되어 있다.
- G6. 리뷰어가 **로그인 없이도** 핵심 흐름을 체험할 수 있다(데모 모드).

### 2.2 비목표 (Non-goals) — 이번 4주에는 하지 않는다
- 네이티브 모바일 앱 (웹 + PWA로 충분)
- 실제 차량(OBD, 커넥티드카) 연동으로 주행거리 자동 수집
- 정비소 예약·결제, 쇼핑 결제
- 다나와 등 공식 API가 없는 사이트 크롤링
- 커뮤니티·리뷰·댓글 기능
- 관리자(어드민) 페이지 — 규칙·차종 데이터는 시드(seed) 파일로 관리
- 다국어

### 2.3 안티골 (Anti-goals) — 동작하더라도 이렇게 되면 실패
- 기능 다섯 개가 **각자 따로 노는 링크 모음**처럼 보이는 것. (핵심은 "내 차 맞춤"이다.)
- 정비 주기를 **공식 권장값처럼 단정**하는 것. 참고용 수치임을 화면에 명시해야 한다.
- 알림이 **스팸처럼** 반복 발송되는 것. 같은 내용은 한 번만 보낸다.
- 포트폴리오로 걸어둔 뒤 몇 달 지나 **조용히 고장 나는 것**(예약 작업 중단, API 키 만료로 빈 화면). 외부 API 실패 시에도 화면은 깨지지 않아야 한다.
- 데모를 보려면 **소셜 로그인부터 해야 하는 것**.

## 3. 사용자와 핵심 시나리오

### 3.1 대상 사용자
- 차량을 1대 보유한 일반 운전자. 정비 주기를 잘 모르고, 보통 "경고등이 뜨거나 정비소에서 말해줘야" 정비한다.
- (포트폴리오 관점) 리뷰어: 5분 안에 서비스의 핵심과 기술적 깊이를 파악하고 싶다.

### 3.2 시나리오 가 — 처음 방문한 운전자
1. 랜딩 페이지에서 "내 차 등록하기"를 누른다.
2. 카카오 또는 구글로 로그인한다.
3. 제조사 → 모델 → 연식 → 연료를 선택한다. (예: 현대 / 아반떼(CN7) / 2021 / 가솔린)
4. 현재 계기판 주행거리를 입력한다. (예: 42,000km)
5. **주행 습관 계산기**로 일 평균 주행거리를 정한다. (예: 출퇴근 편도 18km × 주 5일 + 주말 이틀 합계 40km → (180 + 40) ÷ 7 ≈ 일 평균 31km)
6. (선택) 최근 정비 이력을 입력한다. 모르면 "기억 안 남"을 선택한다.
7. 대시보드에 항목별 정비 현황과 예상 시기가 나타난다.
8. "정비 시기가 되면 알려드릴까요?" → 알림 허용.

### 3.3 시나리오 나 — 3주 뒤 알림을 받은 운전자
1. 휴대폰에 "엔진오일 교체 시기가 다가와요 (약 500km 남음)" 푸시가 온다.
2. 알림을 누르면 엔진오일 상세 화면이 열린다.
3. "근처 정비소 보기"를 누르면 현재 위치 기준 지도에 정비소가 표시된다.
4. 또는 "엔진오일 최저가 보기"를 누르면 네이버 쇼핑 최저가 목록이 나온다.
5. 정비를 마친 뒤 "정비 완료"를 누르고 계기판 주행거리를 입력한다. → 다음 교체 시기가 새로 계산되고, 주행거리 기준점이 보정된다.

### 3.4 시나리오 다 — 포트폴리오 리뷰어
1. 랜딩 페이지에서 "데모로 둘러보기"를 누른다.
2. 미리 준비된 데모 차량(정비 기록과 주행 기록이 쌓인 상태)으로 대시보드에 들어간다.
3. 보정 제안 카드, 계절 정비 카드, "교체 필요" 상태 항목을 바로 본다.
4. 대시보드의 "테스트 알림 받기" 버튼으로 실제 푸시 알림을 받아본다(구독 정보는 저장되지 않음, 4.4).

## 4. 기능 명세

우선순위: **P0** = 핵심, 반드시 완성 / **P1** = 연결 기능, 가볍게 완성 / **P2** = 시간이 남으면

### 4.1 P0 — 핵심 기능

#### 가. 로그인 / 데모 모드
- 소셜 로그인: 카카오, 구글 (Auth.js).
- 데모 모드: 로그인 없이 읽기 전용 데모 계정으로 진입. 데모 데이터는 시드로 생성하며, 데모 계정에서의 수정은 막는다(또는 세션 종료 시 버려지는 임시 사본 — 빌더 재량, 4.4 참고).
- 회원 탈퇴 시 해당 사용자의 모든 데이터(차량, 기록, 구독, 알림)를 삭제한다.

#### 나. 차량 등록·관리
- 입력: 제조사, 모델, 연식, 연료 타입, 별명(선택), 현재 주행거리, 기준 날짜(기본: 오늘).
- 제조사·모델 목록은 서비스가 보유한 **차종 시드 데이터**에서 고른다. 목록에 없으면 "기타"를 고르고 모델명을 직접 입력하며, 연료 타입만으로 규칙을 적용한다.
- MVP는 **사용자당 차량 1대**를 기본 화면으로 다룬다. 데이터 모델은 여러 대를 허용하도록 설계한다(화면상 차량 전환은 P2).

#### 다. 주행 습관 계산기
- 입력 방식 두 가지 중 선택:
  - (a) 직접 입력: 일 평균 km 또는 월 평균 km (월 → 일 환산: ÷ 30.4)
  - (b) 계산기: (출퇴근 편도 거리 × 2 × 출근 일수/주 + 주말 이틀 합계 거리) ÷ 7 → 일 평균(반올림). 예: (18 × 2 × 5 + 40) ÷ 7 = 31.4 → 31km
- 결과: 일 평균 km(정수 반올림)와 월 평균 km를 보여주고, **일 평균만** 저장한다(월 평균은 표시용 계산값).
- 유효 범위: 일 평균 1 ~ 500km. 범위를 벗어나면 입력을 거부하고 이유를 알려준다.

#### 라. 주행거리 추정
- 공식: `추정 주행거리(오늘) = 마지막 실측 주행거리 + 일 평균 km × (오늘 − 마지막 실측일)의 일수`
- "실측"은 사용자가 직접 입력한 계기판 값(등록 시, 정비 완료 시, 수동 업데이트 시)이다.
- 추정값은 저장하지 않고 **요청 시 계산**한다. (저장하는 것은 실측값과 일 평균뿐)
- 화면에는 추정값 옆에 "추정" 표시와 마지막 실측일을 함께 보여준다. (예: "약 42,775km · 11/1 실측 기준")
- 대시보드에 "계기판 값 업데이트" 버튼을 둔다.

#### 마. 정비 규칙 엔진
- 각 정비 항목은 **거리 주기(km)**와 **기간 주기(개월)** 중 하나 또는 둘을 가진다. 둘 다 있으면 **먼저 도달하는 쪽**이 기준이다.
- 규칙은 연료 타입별로 적용 여부와 주기가 다르다. (6장 규칙 테이블)
- 항목별 계산 결과:
  - 마지막 교체 시점(주행거리·날짜) — 정비 기록이 있으면 그것, 없으면 "기준점"(7.3 참고)
  - 다음 교체 시점: `마지막 교체 km + 주기 km`, `마지막 교체일 + 주기 개월`
  - 남은 거리, 남은 기간
  - **예상 도래일**: 거리 기준 예상일(`오늘 + 남은 km ÷ 일 평균`)과 기간 기준일 중 빠른 날
  - 진행률(%) = max(거리 진행률, 기간 진행률)
  - 상태: 7.2의 상태 구간 규칙에 따름
- 엔진은 **순수 함수**(입력: 차량·규칙·기록·오늘 날짜 → 출력: 항목별 결과)로 작성해 단위 테스트한다. DB나 시간에 직접 의존하지 않는다.

#### 바. 정비 현황 대시보드
- 상단: 차량 요약(모델, 추정 주행거리, 일 평균), 계기판 업데이트 버튼.
- 경고 영역: "교체 필요" → "곧 교체" 순으로 정렬된 카드.
- 계절 정비 카드(기능 자), 보정 제안 카드(기능 아) — 해당될 때만.
- 전체 항목 목록: 항목명, 진행 막대, 남은 거리/기간, 예상 도래일, 상태 배지.
- 항목을 누르면 상세 화면(기능 사)으로 이동.

#### 사. 정비 항목 상세 / 정비 기록
- 상세: 항목 설명(무엇이고 왜 교체하는지), 적용된 주기, 계산 근거("마지막 교체 2025-12-01 · 32,000km, 주기 10,000km 또는 12개월"), 정비 기록 목록.
- 연결 버튼: "근처 정비소 보기"(기능 카), "최저가 보기"(기능 타) — 항목에 연결 키워드가 있을 때만.
- **정비 완료 기록**: 날짜(기본 오늘), 주행거리(필수), 비용(선택), 메모(선택). 저장 시:
  1. 정비 기록 추가 → 해당 항목의 다음 교체 시점이 다시 계산됨
  2. 입력한 주행거리를 **실측값**으로도 저장하고 기록과 연결(`maintenance_records.odometer_reading_id`) → 주행거리 추정 기준점 갱신(기능 라)
  3. 단, 실측 저장이 기능 아의 "감소 금지" 규칙에 걸리면(과거 날짜 기록 등) **정비 기록만 저장**하고 실측은 만들지 않으며, 그 사실을 안내한다.
- 기록 수정 시 연결된 실측도 같이 수정(규칙 위반이면 연결 해제), 기록 삭제 시 연결된 실측도 삭제한다.
- 온보딩 3단계에서 입력하는 과거 정비 이력은 **월 단위 근사값**이므로 실측으로 만들지 않는다(날짜는 해당 월 1일로 저장).

#### 아. 주행 패턴 보정 제안
- 기준 실측 = "최신 실측으로부터 180일 이내 중 가장 오래된 값"(너무 오래된 습관 반영 방지).
- 조건: 기준 실측과 최신 실측이 서로 다르고, 두 날짜 사이가 **14일 이상**. (계산식은 7.6)
- 실제 일 평균 = (최신 실측 km − 기준 실측 km) ÷ 두 날짜 사이 일수.
- 설정값과 실제값의 차이가 **20% 이상**이면 대시보드에 제안 카드를 띄운다:
  "입력하신 일 평균 31km보다 실제로는 약 38km 타고 계세요. 바꿀까요? [바꾸기] [그대로 두기]"
- "그대로 두기"를 누르면 다음 실측이 추가될 때까지 다시 띄우지 않는다.
- 실측값이 이전 실측보다 작으면(계기판 오입력) 저장을 거부한다.

#### 자. 계절 정비 안내
- 월 기준으로 계절 체크리스트를 보여준다(6.3 테이블). 연료 타입에 따라 일부 항목은 제외한다.
- 대시보드 카드: 해당 계절 동안 노출. 각 항목에 체크 표시 가능(올해 시즌 기준으로 저장).
- 계절이 시작되는 달의 첫 Cron 실행 때 한 번 푸시 알림(기능 차).

#### 차. 알림 (Web Push + 알림함)
- 알림 권한 요청은 **대시보드를 처음 본 뒤** 사용자가 버튼을 눌렀을 때만 한다(첫 방문 즉시 요청 금지).
- 구독 정보(push subscription)를 서버에 저장한다. 한 사용자가 기기 여러 대를 구독할 수 있다.
- 서버가 매일 1회 Cron으로 알림 대상을 계산해 발송한다(10장).
- 알림 종류:
  - `DUE_SOON`: 항목이 "곧 교체" 상태에 진입했을 때 1회
  - `OVERDUE`: 항목이 "교체 필요" 상태가 되면 첫 알림 1회, 정비 기록 전까지 직전 OVERDUE 알림으로부터 **14일 이상** 지났을 때 재알림. **주기당 총 3회**(첫 알림 + 재알림 2회)까지.
  - `SEASONAL`: 계절 시작 시 1회
  - `CALIBRATION`: 알림 없음(대시보드 카드로만)
  - 정비 기록이 없어 **추정 기준점**(7.3)으로 계산된 항목은 `DUE_SOON`만 보내고 문구를 "~할 때가 됐을 수 있어요 (기록이 없어 추정)"으로 바꾼다. `OVERDUE`는 보내지 않는다.
- **알림함**: 알림 종류가 켜져 있으면 **푸시 구독이 없어도** 알림함에는 기록된다(푸시를 못 받는 환경 대비). 읽음 처리 가능.
- 알림 설정: 종류별 켜기/끄기, 전체 끄기, 구독 기기 목록과 해제. **기본값은 모두 켜짐**(푸시 발송은 구독한 기기가 있을 때만).
- 아이폰(iOS Safari)은 **홈 화면에 추가한 PWA에서만** 푸시를 받을 수 있다. 해당 환경을 감지하면 "홈 화면에 추가하면 알림을 받을 수 있어요" 안내를 보여준다.
- "테스트 알림 보내기" 버튼: 로그인 사용자는 설정 화면에서 자기 구독 기기로 발송, 데모 사용자는 대시보드에서 발송(4.4).

### 4.2 P1 — 연결 기능 (실제 API, 가볍게)

#### 카. 주변 정비소·세차장 지도
- 카카오맵 JavaScript SDK + 장소 검색(services 라이브러리).
- 위치: 브라우저 위치 권한(Geolocation). 거부 시 주소/지역 검색창으로 대체, 기본 위치는 서울시청.
- 검색 카테고리 탭: 세차장, 정비소, 타이어, 주유소(카카오 카테고리 코드 OL7 사용), 전기차 충전소(전기차일 때 기본 탭).
- 결과: 지도 마커 + 목록(이름, 거리, 주소, 전화, 카카오맵 상세 링크).
- 정비 항목 상세에서 들어오면 해당 항목의 지도 키워드로 바로 검색한다(예: 타이어 → "타이어").

#### 타. 차량용품 최저가 비교
- 네이버 검색 API(쇼핑)를 **서버에서** 호출한다(Client Secret 보호).
- 검색어: 사용자가 입력하거나, 정비 항목에서 넘어오면 항목의 쇼핑 키워드 + 차종(예: "아반떼 CN7 에어컨필터").
- 정렬: 가격 오름차순(`sort=asc`), 결과의 `lprice`(최저가), `mallName`, 상품 링크, 이미지 표시.
- 응답 캐시 1시간(11.3).
- 화면에 "가격은 네이버 쇼핑 검색 결과 기준이며 실제와 다를 수 있음" 표기.

#### 파. 차량 소식·신차 뉴스
- 네이버 검색 API(뉴스)를 서버에서 호출.
- 탭: "내 차 소식"(모델명 검색, 예: "아반떼"), "신차 출시"("신차 출시" 검색), "자동차 일반"("자동차"). 검색창으로 자유 검색.
- 표시: 제목, 요약, 언론사 링크, 날짜. HTML 태그(`<b>` 등)와 엔티티는 서버에서 정리한다.
- 응답 캐시 30분.

### 4.3 P2 — 시간이 남으면
- 여러 차량 전환 UI
- 이메일 알림(푸시 보조 채널)
- 기상청 단기예보로 "내일 영하 — 배터리·워셔액 점검" 같은 날씨 기반 알림
- 정비 비용 통계(월별·항목별 차트)
- 다크 모드

### 4.4 데모 모드 상세 (제안)
- 시드 스크립트로 데모 사용자 1명 + 차량 1대(예: 기아 K5 2020 가솔린, 일 평균 35km 설정이지만 실측상 약 45km) + 정비 기록 6~8건 + 실측 4~5건을 생성한다. 데이터는 **오늘 날짜 기준 상대값**으로 만들어서, 언제 열어도 "교체 필요 1개, 곧 교체 2개, 보정 제안 1개"가 보이도록 한다.
- 시드는 배포 시 또는 매일 Cron에서 데모 데이터를 재생성해 상대 날짜를 유지한다.
- 데모 세션은 읽기 전용이 기본이다. 쓰기 시도 시 "데모에서는 저장되지 않아요" 안내. (임시 사본 방식은 빌더 재량)
- 데모 사용자(`users.is_demo = 1`)는 **일일 알림 작업에서 제외**한다. 데모 데이터를 매일 재생성해도 알림이 반복 생성되지 않게 하기 위함이다.
- **데모 테스트 알림**: 데모 대시보드에 "테스트 알림 받기" 버튼을 둔다. 브라우저가 만든 구독 정보를 요청 본문으로 받아 **저장하지 않고 즉시 1건만 발송**한다(`POST /api/push/demo-test`). 남용 방지를 위해 같은 endpoint는 10분에 1회로 제한한다.
- 데모 세션 구현: 데모 사용자로 로그인된 세션을 발급한다(Auth.js 세션 또는 별도 서명 쿠키 — 빌더 재량). 데모 허용 페이지는 5.1 표를 따른다.

- 범위: 국산 주요 제조사(현대, 기아, 제네시스, 쉐보레, 르노코리아, KGM) 현행·직전 세대 인기 모델 + 수입 주요 모델 일부, 총 **60~100개 모델**.
- 필드: 제조사, 모델명, 세대/코드명(선택), 생산 연식 범위, 가능한 연료 타입 목록.
- 데이터 출처: 각 제조사 공식 사이트의 모델 라인업을 수작업 정리(JSON 시드). 공개 API는 사용하지 않는다.
- 정비 규칙은 모델이 아닌 **연료 타입**으로 결정되므로, 시드 정확도가 계산 정확도를 해치지 않는다.

## 7. 핵심 계산 로직 상세

### 7.1 용어
- `today`: 한국 시간(KST, UTC+9) 기준 날짜. 서버는 UTC로 동작하므로 날짜 계산 전에 KST로 변환한다.
- `dailyKm`: 사용자 설정 일 평균 주행거리.
- `latestReading`: 가장 최근 실측(날짜, km).

### 7.2 상태 구간 규칙
각 항목에 대해 거리 기준과 기간 기준을 각각 평가하고 **더 나쁜 상태**를 택한다.

| 상태 | 거리 기준 | 기간 기준 |
|---|---|---|
| `OVERDUE` (교체 필요) | 남은 거리 ≤ 0 | 남은 기간 ≤ 0일 |
| `DUE_SOON` (곧 교체) | 남은 거리 ≤ max(주기의 10%, 500km) | 남은 기간 ≤ 30일 |
| `OK` (양호) | 그 외 | 그 외 |
| `UNKNOWN` (정보 없음) | 정비 기록이 없고 **기간 주기만 있는 항목**(배터리, 와이퍼) — 7.3 | |

### 7.3 기준점(마지막 교체 시점)이 없을 때
정비 기록이 없는 모든 항목에 적용한다(온보딩에서 "기억 안 남"을 고른 항목과 아예 묻지 않은 항목 모두 동일). 그래서 `item_baselines` 테이블은 두지 않는다.
- **거리 주기가 있는 항목**: **차량 연식 시작일(연식의 1월 1일)과 0km**를 출고 시점으로 보고, 그 이후 주기마다 교체했다고 가정해 **"다음 주기 도래 시점"**을 계산한다.
  - 예: 엔진오일(10,000km), 추정 42,775km → 마지막 가정 교체 40,000km → 다음 50,000km
  - 가정 주기 번호 `n = floor(추정 km ÷ 주기 km)`를 알림 중복 방지 키(`cycleKey = guess-{n}`)로 쓴다. 주행거리가 다음 주기로 넘어가면 새 주기로 본다.
  - 기간 주기도 함께 있으면, 기간은 출고일부터 주기 배수로 같은 방식으로 계산하고 더 나쁜 상태를 택한다.
  - 이 방식에서는 항목이 `OVERDUE`가 되지 않는다(늘 다음 주기를 가리키므로). 상태는 `OK` 또는 `DUE_SOON`.
- **기간 주기만 있는 항목**(배터리, 와이퍼): 연식 1월 1일 기준으로 가정하면 같은 연식의 모든 차가 같은 날 도래해 의미가 없으므로, 상태를 `UNKNOWN`으로 두고 "마지막 교체 시기를 알려주세요"를 표시한다. 알림 없음.
- 추정 기준으로 계산된 항목은 화면에 "기록 없음 · 추정 기준" 배지를 달고, 정비 기록을 입력하라고 유도한다.

### 7.4 예상 도래일
- 거리 기준: `today + ceil(남은 km ÷ dailyKm)`일 (남은 km ≤ 0이면 이미 도래)
- 기간 기준: `마지막 교체일 + 주기 개월`
- 예상 도래일 = 둘 중 빠른 날. 표시할 때 어느 기준인지 함께 보여준다("거리 기준" / "기간 기준").

### 7.5 계산 예시 (테스트 케이스로도 사용)
- 차량: 가솔린, dailyKm = 31, 마지막 실측 2026-11-01 · 42,000km, today = 2026-11-26
- 추정 주행거리 = 42,000 + 31 × 25 = **42,775km**
- 엔진오일 기록: 2025-12-01 · 33,300km
  - 다음: 43,300km 또는 2026-12-01
  - 남은 거리 525km → 500km와 10%(1,000km) 중 큰 값 1,000km 이하 → `DUE_SOON`
  - 거리 기준 예상일 = 11/26 + ceil(525/31)=17일 → 2026-12-13
  - 기간 기준 = 2026-12-01 → **예상 도래일 2026-12-01 (기간 기준)**
  - 남은 기간 5일 ≤ 30일 → `DUE_SOON`. 최종 `DUE_SOON`.

### 7.6 보정 제안 계산
- 실측 목록을 날짜순 정렬 → 최신 실측 `r_n`, 그로부터 180일 이내 가장 오래된 실측 `r_0`.
- `r_n.date − r_0.date ≥ 14일`이 아니면 제안 없음.
- `actual = (r_n.km − r_0.km) ÷ 일수`, `diff = |actual − dailyKm| ÷ dailyKm`.
- `diff ≥ 0.2`이고, 사용자가 이 `r_n` 이후로 "그대로 두기"를 누르지 않았으면 제안.

### 7.7 테스트해야 할 경계 사례 (최소)
- 실측 1개뿐 / 같은 날 실측 2개 / 실측값 감소 시도
- 기간 주기만 있는 항목, 거리 주기만 있는 항목
- 전기차에서 엔진오일 항목 미표시
- "기억 안 남" 항목의 기준점 가정 계산
- 연말·윤년을 넘는 기간 계산 (예: 2027-02-29 없음 → 월말 처리)
- KST 자정 직후/직전의 today 계산
- 남은 km가 정확히 0, 정확히 임계값인 경우

## 9. 데이터 모델 (D1 / SQLite)

시간 값은 모두 ISO 문자열(UTC) 또는 `YYYY-MM-DD`(KST 기준 날짜)로 저장한다. 날짜만 의미 있는 값(정비일, 실측일)은 `YYYY-MM-DD`.

### 9.1 인증 (Auth.js 어댑터 표준 테이블)
- `users` (id, name, email, image, created_at, is_demo)
- `accounts`, `sessions`, `verification_tokens` — Auth.js D1/Drizzle 어댑터가 요구하는 형태 그대로.

### 9.2 차종·규칙 (시드, 읽기 전용)
- `vehicle_models`
  - id, maker, name, generation(nullable), year_from, year_to(nullable), fuel_types(JSON 배열)
- `maintenance_items`
  - code(PK, 예: ENGINE_OIL), name, description, map_keyword(nullable), shop_keyword(nullable), sort_order

  - id, item_code(FK), fuel_type, vehicle_model_id(nullable, 차종 예외용), interval_km(nullable), interval_months(nullable)
  - 고유키: (item_code, fuel_type, vehicle_model_id)
- `seasonal_items`
  - id, season(SPRING/SUMMER/FALL/WINTER), label, excluded_fuel_types(JSON 배열), sort_order

### 9.3 사용자 데이터
- `vehicles`
  - id, user_id(FK), vehicle_model_id(FK, nullable), custom_model_name(nullable), model_year, fuel_type, nickname, daily_km, created_at, updated_at
- `odometer_readings` (실측)
  - id, vehicle_id(FK), date, km, source(ONBOARDING/MANUAL/MAINTENANCE), created_at
  - 제약: 같은 차량에서 날짜가 더 늦은데 km가 더 작은 값은 저장 불가(애플리케이션 검증)
- `maintenance_records`
  - id, vehicle_id(FK), item_code(FK), date, km, cost(nullable), memo(nullable), odometer_reading_id(FK, nullable — 기능 사에서 함께 만든 실측), source(ONBOARDING/MANUAL), created_at
- `calibration_dismissals`
  - vehicle_id(PK), dismissed_at_reading_id — "그대로 두기"를 누른 시점의 최신 실측. 그 실측이 삭제되면 행도 삭제(제안이 다시 보일 수 있음).
- `seasonal_checks`
  - vehicle_id, season_key(예: 2026-WINTER), seasonal_item_id, checked_at

### 9.4 알림
- `push_subscriptions`
  - id, user_id, endpoint(UNIQUE), p256dh, auth, user_agent, created_at, last_success_at
- `notification_prefs`
  - user_id(PK), due_soon(bool), overdue(bool), seasonal(bool), all_off(bool)
- `notifications` (알림함 + 중복 방지 기록)
  - id, user_id, vehicle_id, type(DUE_SOON/OVERDUE/SEASONAL/TEST), item_code(nullable), dedupe_key(UNIQUE), title, body, url, created_at, read_at(nullable)
  - `dedupe_key` 예: `DUE_SOON:{vehicleId}:{itemCode}:{cycleKey}`, `OVERDUE:{vehicleId}:{itemCode}:{cycleKey}:{n}`, `SEASONAL:{vehicleId}:2026-WINTER`
  - `cycleKey` = 해당 항목의 마지막 정비 기록 id. 기록이 없으면 `guess-{n}`(7.3) → 정비 기록이 추가되거나 가정 주기가 넘어가면 새 주기로 간주되어 다시 알림 가능

### 9.5 인덱스
- `odometer_readings(vehicle_id, date)`, `maintenance_records(vehicle_id, item_code, date)`, `notifications(user_id, created_at)`, `push_subscriptions(user_id)`

## 10. 알림 시스템 상세

### 10.1 구독 흐름
1. 사용자가 "알림 받기"를 누름 → `Notification.requestPermission()`
2. 허용 시 서비스 워커 등록(`/sw.js`) → `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: VAPID 공개키 })`
3. 구독 정보를 `POST /api/push/subscribe`로 저장(로그인 사용자 기준). 같은 endpoint가 있으면 갱신.
4. 해제 시 `pushSubscription.unsubscribe()` + `DELETE /api/push/subscribe`.

### 10.2 일일 작업 (Cron, 매일 KST 09:00)
```
for each 데모가 아니고 전체 끄기가 아닌 사용자의 차량:   (푸시 구독 유무와 무관)
    결과 = 규칙엔진(차량, 규칙, 기록, 실측, today)
    for each 항목 in 결과 (해당 알림 종류가 켜진 것만):
        if 상태 == DUE_SOON  → 후보(DUE_SOON, cycleKey)
        if 상태 == OVERDUE   → 이 주기의 기존 OVERDUE 알림 수 k 조회
                               k == 0 → 후보(OVERDUE, n=0)
                               0 < k < 3 이고 마지막 OVERDUE 알림이 14일 이상 전 → 후보(OVERDUE, n=k)
    if 오늘이 계절 시작 월이고 이번 시즌 알림 기록 없음 → 후보(SEASONAL)
    후보마다 dedupe_key로 INSERT (이미 있으면 건너뜀)  ← 중복 방지의 핵심
    새로 INSERT된 알림만 → 사용자의 모든 구독 기기로 푸시 발송
       - 410/404 응답 → 해당 구독 삭제
       - 그 외 실패 → 로그만 남기고 계속 (알림함에는 이미 기록됨)
       - 성공 → last_success_at 갱신
같은 사용자의 알림이 여러 개면 한 번의 푸시로 묶는다 ("정비 알림 3건: 엔진오일 외 2건")
데모 데이터 갱신
```
- OVERDUE 재알림 간격은 "진입일"이 아니라 **직전 OVERDUE 알림의 생성 시각**으로 계산한다. 그래서 하루 실행이 빠지거나 실측 입력으로 과거에 이미 도래한 것으로 바뀌어도 알림이 누락되지 않는다.
- 하나의 대시보드에서 기한이 바뀌는 경우(실측·일 평균 수정)에도 dedupe 키가 같으면 다시 보내지 않는다.
- 처리량: 포트폴리오 규모(사용자 수십 명 이하)에서는 한 번의 실행으로 충분하다. 사용자가 늘면 Queue로 분산하는 것이 다음 단계라고 문서(README)에 적어 둔다.

### 10.3 Cron 테스트 경로
- Cloudflare 프리뷰 환경에서는 Cron이 실행되지 않으므로, 같은 작업 함수(`src/server/jobs/daily.ts`)를 호출하는 **보호된 HTTP 경로**(`POST /api/internal/run-daily`, 헤더의 비밀 토큰 필요, 운영에서는 비활성 또는 토큰 필수)를 둔다.
- 로컬에서는 Cloudflare Local Explorer의 Cron 실행 기능으로도 테스트할 수 있다.

### 10.4 알림 내용 예시
- 제목: "엔진오일 교체 시기가 다가와요" / 본문: "약 500km 남았어요 · 12/1 예상" / 클릭: `/maintenance/ENGINE_OIL`
- 제목: "브레이크액 교체 시기가 지났어요" / 본문: "교체한 지 24개월이 지났어요" / 클릭: `/maintenance/BRAKE_FLUID`
- 제목: "겨울철 차량 점검 시즌이에요" / 본문: "배터리, 부동액, 워셔액을 확인해 보세요" / 클릭: `/dashboard`

### 10.5 서비스 워커
- `push` 이벤트: payload(JSON: title, body, url)로 `showNotification`.
- `notificationclick`: 이미 열린 탭이 있으면 그 탭으로 이동, 없으면 새 창으로 `url` 열기.
- PWA `manifest.webmanifest`: 이름, 아이콘(192/512), `display: standalone` — iOS 푸시 조건.

## 11. 외부 API 연동

### 11.1 목록

| 용도 | API | 호출 위치 | 키 보관 |
|---|---|---|---|
| 지도·장소 검색 | 카카오맵 JavaScript SDK (+services) | 브라우저 | JS 키 (공개, 카카오 콘솔에서 **도메인 제한**) |
| 로그인 | 카카오 로그인, 구글 OAuth | 서버(Auth.js) | Worker Secret |
| 최저가 | 네이버 검색 API — 쇼핑 | 서버 | Worker Secret (Client ID/Secret) |
| 뉴스 | 네이버 검색 API — 뉴스 | 서버 | Worker Secret |
| 푸시 | Web Push (VAPID) | 서버 | VAPID 개인키: Worker Secret / 공개키: 공개 환경 변수 |

- 각 API의 일일 호출 한도·이용 약관(출처 표기 등)은 구현 시 콘솔에서 확인해 README에 정리한다.

### 11.2 실패 처리
- 서버 프록시(`/api/shop`, `/api/news`)는 외부 API 실패 시 `502`와 사용자용 메시지를 반환하고, 화면은 대체 문구를 보여준다. 대시보드(핵심 기능)는 외부 API에 **의존하지 않는다**.
- 외부 응답은 zod로 필요한 필드만 검증·추출한 뒤 내려준다(HTML 태그 제거 포함).

### 11.3 캐시
- Workers Cache API(`caches.default`)로 쿼리 문자열 단위 캐시: 쇼핑 1시간, 뉴스 30분.
- 같은 검색어의 반복 호출을 줄여 API 한도를 보호한다.

## 12. 인증 · 보안 · 개인정보

- 모든 사용자 데이터 접근은 **세션의 user_id로 소유권을 검사**한다(다른 사람 vehicle_id 접근 차단). Server Action마다 공통 헬퍼로 강제.
- 모든 입력은 zod로 검증: 주행거리(0 ~ 2,000,000), 일 평균(1 ~ 500), 날짜(미래 불가), 비용(0 이상), 메모 길이(500자).
- 비밀값(OAuth 비밀키, 네이버 Secret, VAPID 개인키, 내부 작업 토큰)은 **Worker Secret**과 **GitHub Actions Secrets**에만 둔다. 저장소에 커밋 금지. `.dev.vars`는 `.gitignore`.
- 내부 작업 경로(`/api/internal/*`)는 비밀 토큰 비교(타이밍 안전 비교) 필수.
- 프록시 경로(`/api/shop`, `/api/news`)는 남용 방지를 위해 검색어 길이 제한(50자) + 캐시. (필요하면 Cloudflare Rate Limiting 규칙 추가 — 빌더 재량)
- 데모 계정은 쓰기 차단.
- 개인정보: 이메일·이름(소셜 로그인 제공값), 차량 정보, 위치(저장하지 않음 — 지도 검색에만 브라우저에서 사용). 개인정보 처리 안내 페이지(간단한 텍스트) 제공, 회원 탈퇴 시 전부 삭제.

## 13. 배포 · CI/CD (GitHub Actions + Cloudflare)

### 13.1 환경
- **production**: Cloudflare Workers (`*.workers.dev` 또는 사용자 도메인), D1 운영 DB
- **preview**: PR별 Workers Preview (Cron 미실행 → 10.3 테스트 경로 사용), D1 프리뷰 DB(또는 로컬)
- **local**: `next dev` / vinext dev + 로컬 D1 (wrangler 로컬 시뮬레이션)

### 13.2 워크플로

`ci.yml` — 모든 PR과 main push:
1. checkout, Node 설정, 의존성 설치(캐시)
2. lint (ESLint), 타입 검사(`tsc --noEmit`)
3. 단위 테스트(Vitest) — 도메인 로직 커버리지 리포트
4. 빌드
5. (PR) Workers Preview 배포 후 PR에 프리뷰 URL 코멘트 — 빌더 재량

`deploy.yml` — main push (CI 통과 후):
1. 빌드
2. `wrangler d1 migrations apply <DB> --remote` (마이그레이션 먼저)
3. Worker 배포(`cloudflare/wrangler-action` 또는 `cf deploy`)
4. 배포 후 스모크 테스트: `/` 와 `/api/health` 200 확인

### 13.3 필요한 Secrets
- GitHub: `CLOUDFLARE_API_TOKEN`(Workers 편집 + D1 편집 권한, 해당 계정만), `CLOUDFLARE_ACCOUNT_ID`
- Worker Secret: `AUTH_SECRET`, `AUTH_KAKAO_ID/SECRET`, `AUTH_GOOGLE_ID/SECRET`, `NAVER_CLIENT_ID/SECRET`, `VAPID_PRIVATE_KEY`, `INTERNAL_JOB_TOKEN`
- 공개 변수: `NEXT_PUBLIC_KAKAO_MAP_KEY`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY`

### 13.4 Cron 설정
- Workers 설정에 `crons = ["0 0 * * *"]` (UTC 00:00 = KST 09:00).
- **GitHub Actions의 schedule 기능은 쓰지 않는다**: 저장소에 60일간 활동이 없으면 예약 워크플로가 자동 비활성화되어, 포트폴리오로 걸어둔 뒤 알림이 멈출 수 있기 때문이다.

## 17. 검토한 접근 방식 (Approaches)

### 가. Next.js 하나로 풀스택 — **선택**
Route Handler·Server Action이 백엔드, 저장소 하나. 백엔드 로직이 직접 작성한 코드로 남아 포트폴리오 목적에 맞고, 1인 4주에 현실적이다.

### 나. Next.js + Supabase에 백엔드 위임 — 기각
가장 빠르지만 핵심 로직이 서비스 설정 속으로 들어가 "백엔드를 직접 구축"하려는 목적과 어긋난다.

### 다. Next.js 프론트 + 별도 백엔드 서버(NestJS 등) — 기각
백엔드를 가장 본격적으로 보여주지만, 서버 두 개의 구축·배포 비용 때문에 4주 안에 핵심 기능 완성도가 떨어질 위험이 크다.

### 가안의 배포 대상 결정: Vercel → Cloudflare + GitHub Actions (사용자 결정)
이 결정에 따라 다음을 함께 바꿨다(작성자 판단):
- 실행: vinext(Cloudflare가 새 Next.js 앱에 권장하는 방식). OpenNext는 대체안.
- DB: Postgres → D1. Worker 바인딩으로 연결 관리가 필요 없고 무료.
- ORM: Prisma → Drizzle. D1 지원과 마이그레이션 생성이 자연스럽다(Prisma의 D1 마이그레이션은 아직 얼리 액세스).
- 예약 작업: Cloudflare Cron Trigger. GitHub Actions schedule은 60일 비활동 시 꺼지는 문제로 제외.

- 데모 모드(기능 가, 4.4)와 그 데이터 구성
- 알림 발송 시각 KST 09:00, 하루 묶음 발송
- 기술 세부: vinext, D1, Drizzle, Auth.js, 전역 CSS, Vitest, Playwright
- 사용자당 차량 1대 화면(MVP), 데이터 모델은 다수 허용

### 18.3 빌더 재량 (설계에 영향 없는 세부)
